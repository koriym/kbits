# PHP 8.5.12の緊急リリースにpixivはどう対応したか

**原題:** PHP 8.5.12の緊急リリースにpixivはどう対応したか  
**著者:** picopico（pixiv Platform Division Infrastructure Unit）  
**公開日:** 2026-10-22  
**ソースURL:** [inside.pixiv.blog](https://inside.pixiv.blog/2026/10/22/193321)  
**アーカイブ日:** 2026-10-26

## 要約

2026年10月21日、PHPに深刻な脆弱性（通称PHP2Shell）が見つかり、緊急のセキュリティリリースが予告された。ピクシブは影響を受ける可能性のあるサービスを同日19時に事前にメンテナンスモードへ入れ、パッチの公開を待って適用する方針を取った。これはpixivの稼働環境をベアメタルのApache HTTP ServerからKubernetesへ完全移行した翌週にあたり、移行後初のPHPバージョンアップでもあった。記事は、22時41分のパッチ公開から23時16分のメンテナンス解除までの約30分に何をしたかを、それを支えるビルド・デプロイ基盤とあわせて説明する。

### 事前準備：公式イメージを待たずにビルドできるようにしておく

pixivはDocker HubのDocker Official ImageのPHPを利用している。当初はパッチ版イメージの公開後に更新する予定だったが、ソース公開後にイメージがすぐ出るか分からず、出たとしてもDocker Hubへのアクセス集中が懸念された。そこで、公式イメージを更新する経路と、PHPをソースから自前でビルドする経路の2種類のマージリクエストを用意した。

ソースからのビルドは、docker-library/phpをローカルにcloneし、現在使っているイメージと同じコンテキスト（8.5/trixie配下のcliとapache）をリポジトリ内にコピーし、Docker BuildxのBakeにtargetとして追加してPHPのバージョンだけ差し替えられるようにした。Dockerfile側の変更は、PHP_VERSION、PHP_URL、PHP_ASC_URL、PHP_SHA256の各ENVを8.5.11から8.5.12へ書き換えるだけである。Bakeのcontexts機能で複数ディレクトリを別々のビルドコンテキストとして取り込めるため、アプリケーションのDockerfileはほぼ書き換えずに済んだ。あわせてベースイメージをビルド用ノードに事前取得し、ビルド時にDocker Hubへ取りに行く必要をなくした。

もう一つの事前準備として、複数ドメインのメンテナンスモードを一括解除するスクリプトを用意した。通常はAnsibleで構成を管理しAWXで適用しているが、速度を優先して手動実行できる形にした。

### コンテナビルド：6分でフルビルドを行うCI基盤

22時41分、予定の23時より早くセキュリティアップデート版が公開されたことに気づき、バージョンとSHA256を確認してビルドを開始した。PHPのバージョンアップはほぼフルビルドになり本来は長時間かかるが、数GBあるイメージを6分でビルドできた。

その基盤として、1日30回のリリースを支えるCIにAMD EPYC 2（64コア128スレッド）のノードをSelf-hosted GitLab Runnerとして使っている。このノードはリポジトリやパッケージをキャッシュしており、約5万件のPHP/MySQL/Redisとの結合テストをマルチスレッドで1分以内に完了させる。さらに同じノードにstandaloneのBuildKitが常駐し、CIコンテナからUnixドメインソケットで接続してビルドする。BuildKitが常時稼働するためNVMeディスクにビルドキャッシュを保持でき、エフェメラルなCI環境でもレジストリキャッシュのようなネットワーク転送のオーバーヘッドなしに高速なキャッシュが使える。ディストリビューションのパッケージやComposerのキャッシュも永続化されているので、フルビルドでも恩恵がある。

Dockerfileにも工夫がある。通常、ベースイメージが変わると後続のレイヤーはすべてキャッシュミスするが、COPY --linkを使うと前のレイヤーが再実行されても独立してキャッシュヒットさせられる。assetsのようにデータ量の重いレイヤーに適用することで、ベースイメージ変更後もキャッシュが再ヒットし、Kubernetesノードがイメージを取得する際の転送量も減る。今回はほぼフルビルドだったにもかかわらず、転送量を3〜4割削減できた。

### デプロイ：Kubernetesクラスタへのロールアウト

pixivはPHP本体とアプリケーションコードを1つのコンテナイメージに入れているため、PHPのバージョンアップも普段のデプロイと同じく新しいイメージへの差し替えで完了する。社内のデプロイツールが対象コミットのイメージのビルド完了を検知すると、Kubernetes manifestのイメージタグを更新するコミットを自動で行い、Argo CDがGitOpsでクラスタへ反映する。

配布経路にも工夫がある。GitLabのイメージレジストリとKubernetesクラスタは隔離されたネットワークにあり、特定のNAT Gatewayノードを通る必要がある。pixivのイメージサイズでは数十ノードが一斉にpullして100GB以上の通信が発生し、NAT Gatewayが輻輳する問題があった。そこでクラスタと同一ネットワーク内のCI Runnerにpull-throughキャッシュとして動くregistry proxyを置き、外部レジストリから取得するのはproxyだけ、各ノードはLAN内の10G回線でproxyからpullする構成にした。この結果、ベースイメージが変わってフルビルドした今回でも10Gbps弱で転送し、総転送量200GB弱の配布が5分以内に終わった。

その後、ステージング環境で新バージョンのPHPが動くことを確認し、通常のパッチバージョンアップと同じく配布物のハッシュと署名の確認、イメージの起動テスト、動作確認を経てメンテナンスモードを解除した。解除直後は前日同時刻と比べたリクエスト量の割合とKubernetesのリソース使用状況を監視した。事前にHPAのminReplicasを上げて十分なリソースを確保していたため、問題は起きなかった。

### たまたまうまくいったところと当日のトラブル

著者はすべてが計画どおりだったわけではないと明記し、三つの問題を挙げる。

第一に、メンテナンスモードが実装されていない箇所があった。主要サービスには実装されていたが、今回はPHPのサービスすべてが対象であり、外部公開している全エンドポイントを遮断する必要があった。既存の実装を流用して全エンドポイントをメンテナンスモードに入れられる状態にし、19時ちょうどに間に合わせた。

第二に、ピクシブ百科事典はpixivとは別のビルド基盤を使っており、多めのリソースを割いていたにもかかわらず、前述の基盤と比べて倍の12分かかった。ただしアプリケーションの規模が小さくロールアウトは短時間で終わったため、結果として同時にメンテナンスを明けることができた。

第三に、PECLが不安定になった。pixivはPHP拡張モジュールをPECLから取得する仕組みを使っていたが、脆弱性発表当日は日中からpecl.php.netへの接続が不安定で、ビルド中に拡張のダウンロードで失敗する恐れがあった。PECLはすでにdeprecatedで、後継としてPIE（PHP Installer for Extensions）が開発されている。PIEはComposerと同じくPackagistを通じて拡張を配布し、pecl.php.netのインフラに依存しない。ピクシブ百科事典は前もって移行し、pixivは当日には間に合わなかったが、運よく過負荷の影響を受ける前にビルドを完了できた。翌10月22日にはpixivもPIEへの切り替えを完了している。著者は、PHP拡張を使っている読者にビルドがPECLに依存していないか確認し、PIEへの移行を検討するよう勧めている。

### おわりに

記事はビルドとデプロイを中心に述べたが、当日はインシデントコマンド、ユーザー告知、各プロダクトでのメンテナンス対応や動作確認など多くの人がそれぞれの役割を果たしたことが、約30分での復旧につながったと締めくくる。同時に、今回うまくいったのはいくつかの条件がたまたま揃っていたからでもあり、修正内容によってはPHP拡張の対応を待つ必要があったり、公式イメージを待つほうが安全な場合もあるため、毎回この手順で済むとは限らないと注意している。

## 論評

この記事の価値は、PHP2Shellという事件そのものではなく、「ランタイムの緊急更新」という繰り返し起こる事態に対して、どの層にどんな備えがあれば30分で復旧できるのかを、実測値と失敗込みで分解して見せている点にある。

最も再利用価値が高いのは事前準備の発想である。緊急時に最も不確かなのは自分たちの作業速度ではなく、公式イメージの公開タイミングやDocker Hub、pecl.php.netといった共有インフラの可用性である。著者はこの不確実性を見越して、公式イメージを待つ経路とソースからビルドする経路の両方を用意した。しかもソースビルドはdocker-library/phpのコンテキストをそのままBakeのtargetとして取り込み、バージョン関連のENVだけを差し替える形にしている。公式のビルド定義を再利用しつつ供給元への依存だけを切り離すこの手法は、Official Imageに依存する多くの組織でそのまま使える。

ビルド基盤の設計も、個々の要素は既知でも組み合わせとして学ぶところが多い。常駐するstandaloneのBuildKitにUnixドメインソケットで接続し、NVMe上にキャッシュを持たせる構成は、エフェメラルなCIとキャッシュの永続性という相反する要求を同じノード内で解決している。COPY --linkでベースイメージ変更後もアセット層をキャッシュヒットさせ、ビルド時間だけでなくノードへの転送量まで3〜4割減らした観察は、Dockerfileの一機能が配布コストにまで効く具体例として貴重である。registry proxyも同様で、NAT Gatewayの輻輳という経路上のボトルネックを、クラスタと同一ネットワークのpull-throughキャッシュで回避し、200GB弱を5分以内に配った数字が添えられている。

もう一つ注目すべきは、PHP本体とアプリケーションを1つのイメージに同梱しているため、PHPのバージョンアップが普段のデプロイと同じ操作で済む点である。緊急対応の速さは当日の機転ではなく、日常の変更経路と非常時の変更経路を同じにしておく設計から生まれている。Argo CDによるGitOpsやHPAのminReplicasを事前に上げる判断も、同じ思想の延長にある。

一方で、記事が自ら挙げる失敗は、この種の対応で見落とされがちな箇所を正確に指している。メンテナンスモードが主要サービスにしかなかったこと、別基盤のサービスのビルドが倍かかったこと、PECLという外部依存が当日まで残っていたことは、いずれも「主要な経路は整っているが周辺が追いついていない」という典型的な状態である。著者が「たまたま揃った」と繰り返し、修正内容次第では公式イメージを待つほうが安全な場合もあると限界を明記しているのは、成功談として消費されることへの抑制として評価できる。

全体として、本記事は自社基盤の紹介にとどまらず、緊急更新に備える設計原則を実績ある数字とともに示している。コンテナ基盤で言語ランタイムを運用する読者にとって、供給元への依存を事前に切り離す、ビルドキャッシュを永続化する、配布経路のボトルネックを局所化する、非常時の操作を日常の操作と一致させる、という四点を点検する材料になる。
