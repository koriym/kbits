# エンジニアが解くべき新しい問題群

**著者:** Katelyn Lesse  
**公開日:** 2026-10-26

## 要約

著者はまず、多くのソフトウェアエンジニアが「アイデンティティの危機」としか言いようのない状況を通過していると述べる。仕事の中身は大きく変わり、落ち込んでいる人もいれば、人生で最高の時間を過ごしている人もいる。そのなかで著者が特に注目し、今後一、二年のエンジニアリングを楽しみにしている理由がひとつある。それは、AIが本来生み出せるはずの素晴らしい成果は、ソフトウェアエンジニアがそれを可能にする問題を解かない限り実現しない、という事実である。これは存在に関わる問題であり、だからこそ率直に言って楽しく、ソフトウェアエンジニアでいるには信じがたいほど良い時代だと著者は位置づける。

### マルチエージェントシステムが問題を生んでいる

これらの問題を生んでいるのはマルチエージェントシステムである。著者はエージェントの発展を段階的に描く。最初は人間がループに入る基本的なチャットだった。次にモデルが難しい問題に長時間取り組めるようになり、エージェントシステムはクラウドへ移っていった。それと並行してモデル同士が協働する能力も向上し、人々は基本的なマルチエージェントシステムを組み始めた。あるタスクのためにオーケストレーターがサブエージェントを生成する構成や、実行以外の役割、たとえば採点、助言、あるいは「夢を見る」といった役割をエージェントに与えて成果を高める構成がその例である。

そして今、一部の人々は、本格的な研究、発見、ハードウェア設計といった世界で最も困難で重要な問題に挑むため、真に驚くべきマルチエージェントシステムを構築し始めている。著者が描く像は、数千のエージェントがそうした成果に向けて永続的に働き続ける姿である。これに伴って新しいソフトウェアエンジニアリングの問題群が現れており、すでにその兆候は見えているという。

インフラはよりバースト的なワークロードを扱えるよう進化しなければならない。エージェントを識別し、協働させ、取るべき行動を可能にし、取るべきでない行動を防ぐための適切な認証と認可が必要になる。信頼できないコードやコンテンツに対しては、セキュリティと適切な分離が決定的に重要である。そして監視の仕組みと、システムが誤った方向へ逸れたときにその場で止める能力が欠かせない。

モデルは今後も良くなり続け、この種のマルチエージェントシステムは本当に強力になる。しかしその力を実際に解き放ち、病気の治癒のような良い結果を生むと世界が信頼できるようにするには、ソフトウェアエンジニアがこれらの問題をすべて解かなければならない。これが著者の中心的な主張である。

### インフラの進化

ソフトウェア産業はKubernetesの上に積み上げてきたが、Kubernetesはステートレスで複製されるアプリ、あるいは安定した個数を持つステートフルなPodの集合のために設計されたものである。エージェントはまったく異なる。本質的に、分離された、ステートフルな、単一インスタンスのワークロードである。作業の合間に任意の長さでアイドル状態になり、多くの時間をツール、モデル推論、他のエージェント、人間の入力を待つことに費やす。ワークロードによっては高速な起動が必要であり、別のものは計算資源の浪費を避ける必要があり、さらに別のものは途方もないスケールを必要とする。著者によれば、優れたエンジニアたちがこの問題領域に強く取り組んでおり、AIインフラ企業が新しいファイルシステムやサンドボックスの提供を構築し、Googleのチームが新しいランタイムとしてAgent Substrateを構築している例を挙げる。それでも、解明すべきことは山ほど残っている。

### アイデンティティとアクセス

エージェントの認証、つまりある行動を取ったエージェントを識別する問題がある。この領域は、マイクロサービスの世界で構築され鍛えられてきた部品、たとえば静的な鍵ではなく短命の証明書を使うワークロードアイデンティティといった考え方の恩恵を受けられる。人々はこうした概念をエージェントへ適用し始めている。

一方で、エージェントの認可、すなわちエージェントに何を許すかという問題領域は、はるかに未開拓である。多くのエージェントは人間の代理として働き、その人間のアイデンティティと資格情報を使ってさまざまなシステムにアクセスし、行動を取る。ここにはすでに問題が含まれている。ある行動を取ったのが実際の人間ではなくエージェントであったことを、どう識別するかである。しかし、この「代理（on-behalf-of、OBO）」構成にはさらに深い問題がある。それは同意である。マルチエージェントシステムが数週間にわたって働くとき、人間はどうすればエージェントに許す行動を意味のある形で承認できるのか。ツール呼び出しの自動承認のようなエージェントプラットフォームの機能は助けになるが、大規模に正しくやるには、より深い権限設計が必要になる。そのうえで、エージェントが自分自身のアイデンティティで働く場合はさらに未解決であり、それをエージェント同士の協働にどう適用するか、つまりあるエージェントが何かを依頼してきた別のエージェントをどう信頼するか、という問いが残る。

### セキュリティと分離

ここ数か月、特にここ数週間、業界がパッチを当てられる速度を上回るペースで脆弱性が表面化しており、その多くは多数のシステムが依存する重要な中核ソフトウェアにある。そのうえで、その中核ソフトウェアの上に数千の永続的なエージェントが走り、信頼できないコードを書き、信頼できないコンテンツを読む世界を想像してほしい、と著者は促す。未修正の脆弱性はその世界でははるかに危険になる。したがって、ソフトウェアエンジニアにとって最も重要な仕事のひとつは、カーネル、ブラウザ、ランタイム、共通ライブラリといったソフトウェアをどう硬化させるかについて創造的になることである。

マルチエージェントシステムはここにもうひとつのひねりを加える。侵害されたエージェントは、注入された指示を協働相手のエージェントに渡しうる。そしてその指示はメモリに残り、将来のエージェントが誤って信頼することになりうる。爆発半径が現実のものになる。最初のエージェントが侵害されたとき、マルチエージェントシステムのどれだけが危険にさらされるのか。この世界では分離が重要になり、エージェントは行動を取るために強く分離されたサンドボックス実行環境を使うべきだと著者は述べる。この点については以前に別の文章で書いた、と著者は付記している。

### 監視と停止

最後に、マルチエージェントシステムが良い方向に働いていることを確認し、そうでなければ捕捉して遮断するためのツールが必要である。エージェントをまたぐOpenTelemetryによるトレーシングが必要であり、エージェントが自分のトレースや他のエージェントのトレースを決して改変できないようにしなければならない。監視が発動できるキルスイッチが必要であり、それはシステム全体を一度に本当に止め、その資格情報を断つものでなければならない。そして本当に難しいのは、システムがいつ誤った方向に進んでいるかをどう知るかである。問題を解こうとする善意の粘り強さは、悪意とよく似て見える。許可リストにないドメインへ繰り返し到達を試みる、といった振る舞いがその例である。

### ソフトウェアエンジニアは興奮すべきだ

結びで著者は、自分の知識と技能がもう重要ではなくなると考えてアイデンティティの危機を感じているエンジニアに語りかける。あなたとあなたの技能こそが、これらの問題に取り組めるかどうか、マルチエージェントシステムが世界で最も困難な問題を解けるかどうかの分かれ目になりうる。これらの領域に深く入り、新しいことを学び、意見を形成することができるし、そうすべきである。この問題領域の多くは新しい解決策に向けて大きく開かれており、自分の技能を投じるのに信じがたいほど刺激的な時代だと述べて締めくくる。

## 論評

本稿の価値は、エージェントを論じる視点の階層にある。単一のエージェントにどんな環境や制約を与えるか、あるいは個々の実行環境の権限をどう絞るかという議論はすでに多いが、著者は数千のエージェントが数週間にわたって永続的に協働する状態を前提に置き、その規模で初めて立ち上がる問題を四つの領域に切り分けている。Kubernetesが想定するステートレスで複製可能なワークロードと、分離されステートフルで単一インスタンスであり長時間アイドルするエージェントとの不一致という指摘は、ランタイムの設計前提そのものを問い直すものであり、モデルの能力やプロンプト設計の議論とは別の層にある。

個々の論点も具体的である。代理構成において人間の行動とエージェントの行動を区別する必要、作業が数週間に及ぶときに事前承認が意味を失うという同意の問題、エージェントが固有のアイデンティティで互いを信頼する仕組みの不在、侵害された一つのエージェントの指示がメモリを介して将来のエージェントへ伝播する爆発半径、エージェントが自他のトレースを改変できないことの要件、資格情報まで断ち切るキルスイッチ、そして善意の粘り強さと悪意ある挙動の見分けにくさといった点は、いずれも観察に基づく未解決問題として提示されており、解決策が出揃った後も、何が課題だったかを示す基準点として参照できる。

一方で本稿は問題の地図であって、解法を示すものではない。各領域は一段落程度で描かれ、証拠や実装の詳細は与えられない。その意味で、本稿は特定の手法を学ぶための文献ではなく、マルチエージェントのプラットフォーム層にどのような空白があるかを俯瞰し、エンジニアがどこに深く入るべきかを判断するための出発点として読むのが適切である。エンジニアの役割が失われるのではなく、新しい問題群の解決者として再定義されるという主張は、技術の変化に対する態度の指針としても長く意味を持つだろう。
